# Distributed Tracing for Embedded Systems (tracing-defmt)

## Objective
To achieve flawless, disambiguated, distributed OpenTelemetry tracing across a bare-metal microcontroller (`rpi-pico`), a cloud service (`coap-server`), and a frontend application (`foobar-core`). 

## The Current State & Limitations
Currently, `tracing-defmt` provides syntax compatibility with the host `tracing` crate, mapping `#[instrument]` and `info!` macros directly to `defmt`. 
The host-side `TraceDecoder` attempts to reconstruct spans by maintaining a single stateful stack.

**Critical Flaws Discovered:**
1. **Task Disambiguation:** `defmt` streams are globally multiplexed. If two `embassy` tasks run concurrently, the host decoder's single `span_stack` will incorrectly interleave their spans and logs, destroying parent-child relationships.
2. **Disconnected Root Traces:** Because the OpenTelemetry `TraceId` and `SpanId` are generated by the host *after* the logs leave the device, the device has no knowledge of its own Trace Context. It cannot pass a Context to the Cloud, resulting in disjointed traces in Grafana.

## Core Requirements
To solve these issues, the updated architecture must guarantee:
1. **Device-Generated Contexts:** The microcontroller must generate (or inherit) and own the OpenTelemetry `TraceId` and `SpanId` for actions it initiates.
2. **Concurrency Safety:** Logs emitted by concurrent `embassy` tasks must be perfectly disambiguated by the host decoder.
3. **Bandwidth Efficiency:** The solution must minimize the number of bytes injected into the `defmt` stream to avoid overflowing constrained TCP/UART buffers.

## Architectural Approaches for Investigation

We need to investigate three distinct approaches to injecting the 24-byte `TraceContext` (`[u8; 16]` TraceId + `[u8; 8]` SpanId) into the telemetry stream to disambiguate tasks.

### Approach 1: Explicit Macro Injection (The "Heavy" Way)
Modify the `tracing-defmt` macros (`info!`, `span!`, etc.) to explicitly require or automatically pull a `TraceContext`, physically appending the 24 bytes to every single `defmt` log payload.

* **Mechanism:** 
  `defmt::info!("{=[u8;16]}:{=[u8;8]} Temperature is {}C", ctx.trace_id, ctx.span_id, temp);`
* **Pros:** 
  - Perfect trace disambiguation. 
  - The host decoder is completely stateless; every log frame inherently knows exactly where it belongs.
* **Cons:** 
  - Massive bandwidth bloat. A highly compressed 5-byte `defmt` log becomes a 29-byte log (a 500% increase).
  - Increased `.text` (Flash) footprint due to passing the 24-byte struct into every macro invocation.
* **Investigation Needed:** Profile the exact bandwidth penalty under heavy load (e.g., 100Hz telemetry) to see if the `embassy-net` TCP buffers stall.

### Approach 2: Embassy Task-Local Storage + Custom Defmt Transport
Store the active `TraceContext` in the `embassy_executor`'s Task-Local Storage (TLS). Write a custom global `defmt` logger/transport that automatically prepends the task's active `TraceContext` to the binary frame *before* it hits the network socket.

* **Mechanism:** Application code sets the TLS context. The `defmt` global logger intercepts the encoded binary frame, reads the TLS context, and injects `[24 bytes context][defmt payload]` into the TCP stream.
* **Pros:** 
  - Application code and macros remain completely unmodified. 
  - Context is guaranteed to map correctly to the executing task.
* **Cons:** 
  - Heavily couples the tracing solution to the `embassy` executor. 
  - Still incurs the 24-byte bandwidth penalty per network packet (though potentially less per *log* if defmt batches multiple logs into a single flush).
* **Investigation Needed:** Determine if `defmt`'s global logger allows intercepting and prepending data before the encoding ring-buffer flushes.

### Approach 3: Context Switching "Markers" (The Stateful/Bandwidth-Optimized Way)
Instead of appending 24 bytes to *every* log, the device only emits the `TraceContext` when the `embassy` executor yields or switches tasks. The host `TraceDecoder` maintains a stateful mapping of "Active Contexts."

* **Mechanism:** 
  Whenever an `embassy` task wakes up, it emits a cheap, specific `defmt` marker: `defmt::trace!("__CTX_SWITCH__: {=[u8;16]}", trace_id)`. The host decoder updates its internal pointer. All subsequent standard `defmt` logs (which are just 5 bytes) are mapped to that active Trace ID until a new `__CTX_SWITCH__` marker arrives.
* **Pros:** 
  - Drastically reduces bandwidth overhead. You only pay the 24-byte penalty during a task context switch, not per log line.
* **Cons:** 
  - Requires writing an `embassy` executor extension or `Drop` guard that reliably fires on every task wake/sleep.
  - If a TCP packet containing the `__CTX_SWITCH__` marker drops, all subsequent logs will be mapped to the wrong trace until the next switch.
* **Investigation Needed:** Can we hook into `embassy_executor::Executor::poll` or use task-local `Drop` guards to reliably emit these markers?
